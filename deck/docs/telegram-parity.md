## Four-layer boundary

- **Transport:** standalone supervised Bun process consuming Telegram new-message updates. A failure cannot stop the deck.
- **Identity:** the configured Telegram bot (not the Captain's account, and never Hermes).
- **Invocation:** authorized DMs initially default to task intake; their saved preference can select capture or chat. Groups first require an allowed chat and allowed or paired sender, plus an allowed, non-ignored topic, then a command, leading standalone `@bot_username`, reply or configured wake pattern unless free response applies. A username inside prose, a URL or TOML is data, not an invocation. Accepted text/captions remain unchanged. No invocation choice bypasses identity/topic restrictions.
- **Capabilities:** authorized senders share the Captain-configured deck authority; intake only files cards/inbox items. Explicit chat uses the existing deck session/tool policy, not a new unrestricted runner. Read-only card metadata describes future #101 execution; this bridge never claims to enforce an execution sandbox itself.

Telegram message identity (chat/topic/message ID) supplies a durable
`Idempotency-Key` for capture and each decomposed card index. The inbox API
commits each create/promotion receipt in the same SQLite transaction as its
mutation. Redelivery after a bridge/server restart returns the original result
instead of creating another item/card, including a restart between creation and
promotion. Unkeyed recurring-template promotions keep their existing behavior.
Authorized task/capture updates are journaled in the bridge's SQLite database
before its next poll can confirm them to Telegram. Successful intake clears the
journal entry; interrupted/failed intake is replayed in update order after
restart using the same server receipt keys. Polling and `/stop` remain responsive
while a conversation queue is busy; pending ordinary chat turns are not replayed.
`/stop` also cancels chats queued or awaiting session startup in its conversation.
The cancellation signal follows subscription startup so a late ready frame
cannot submit an already-cancelled prompt; later `/chat` commands remain usable.
